# Operator UI prototype: repository audit

This audit compares the supplied **Content Laboratory Master Plan**, especially section 16 and its related production flows, with the source inspected before the prototype. The plan is a proposed target design. Existing code is evidence of the current implementation. Neither establishes complete or correct behaviour on its own.

The baseline was inspected on 9 September 2026. Classifications below describe that baseline. This is a **source audit**, not a claim that the real API, workers, providers or publishing workflows were tested end to end.

## Current implementation baseline

The active Next.js UI was an empty home-page shell with a CSS reset. The former UI had been deliberately archived and was excluded from this prototype's design and implementation. The repository retained server-side API proxies, an operator context helper, shared types and a substantial Python backend.

The installed graph was used to locate relationships, followed by source verification. After an initial read-only adjacency fallback, graphify queries were made working through the bundled Python runtime with the installed graphify package path. The standalone Windows launcher remains broken. Graph labels and edges were treated as navigation evidence, not guarantees of correctness. The integrated verification report records the post-implementation AST update.

## Prototype coverage and boundaries

The prototype introduces a fresh operator experience around these principal workspaces:

- **Pages:** editable purpose, audience, voice, topics, locale, format, colour, disclosures and explicit inherited/override production budget.
- **Ideas:** evidence, freshness and fit; hold/reject/reconsider; create a connected content brief.
- **Content:** brief, hook, blueprint, asset selection, mandatory ingredients, scene/timeline/object editing, preview, execution, review and publication.
- **Asset Registry:** asset/version/representation detail, readiness, rights, lineage, sample intake/review and eligible selection.
- **Asset packs:** separate planning, acquisition authorisation and fulfilment; item-level route, reason, cost, gaps and ready-subset creation.
- **Operations and review:** visible attempts, costs and failures; candidate comparison; exact package approval/rejection and revision history.
- **Publication:** approved-package preparation and simulated manual post confirmation as separate decisions.
- **Learning:** nullable observations, maturity, experiment rules and reviewed policy proposals in shadow mode.

The interface is typed through [`domain.ts`](../apps/web/app/prototype/domain.ts) and calls an explicit mock service boundary. Existing real API proxies are not the prototype's service implementation. Database migrations, provider execution, real publishing and production authentication are deliberately deferred.

Local composition editing and previews are UI functionality. Simulated generation, provider outcomes, costs, QA measures, packages, metrics and publications do not demonstrate a working media backend. An exported prototype handoff contains its actual plan and sample records; no final video is fabricated.

## Conflicts to resolve before backend integration

1. Map the prototype's immutable revisions and exact approvals to durable content/export records; do not simply reuse mutable reel metadata as the approval ledger.
2. Introduce scene-instance identity independent of asset identity and remove the repeated-instance limitation in the current usage key.
3. Reconcile frame/rational-FPS UI timing with existing seconds-based canonical structures and validate planned/compiled/measured timing explicitly.
4. Reconcile source rights at the representation and intended-use level; a generated-source label must not silently certify all eligibility requirements.
5. Preserve the already implemented resolved-policy provenance. Do not reintroduce the stale hidden-default behaviour described in the proposed plan.
6. Replace generic succeeded idea scaffolds with genuine editorial planning outcomes before presenting the backend as complete.
7. Require exact approval, real post reference and actual post timestamp in the manual publication contract.
8. Define enforced backend role scopes, money reservation/reconciliation and experiment observation contracts separately from UI role previews and illustrative data.

This document records source findings and prototype scope. Runtime verification and local-opening instructions belong to the integrated delivery report and must only be marked passed after execution.
